# ผลการทดสอบระบบ LeaveEasy — 2026-09-20

## 1. สภาพแวดล้อมที่ทดสอบ

- **วันที่ทดสอบ:** 2026-09-20
- **URL ที่ทดสอบ:** http://localhost:3000 (รันด้วย `npx serve -l 3000 .` — พบว่ามี server รันอยู่แล้วที่พอร์ตนี้ก่อนเริ่มทดสอบ และยืนยันแล้วว่าเป็นแอป LeaveEasy ตัวที่ถูกต้อง: หน้าแรกมีคำว่า "LeaveEasy" และข้อความภาษาไทยครบ)
- **เครื่องมือทดสอบ:** Playwright MCP (`mcp__playwright__*`) ควบคุมเบราว์เซอร์จริง
- **สถานะการตั้งค่า Firebase:** `js/firebase-config.js` **ยังเป็น placeholder ทุกช่อง** (`apiKey`, `authDomain`, `projectId`, `storageBucket`, `messagingSenderId`, `appId` ทั้งหมดเป็นข้อความ "ใส่ค่าจาก Firebase Console") — ตรวจด้วย `git log` แล้วพบว่าไฟล์นี้ถูกคอมมิตครั้งเดียวและยังคงเป็น placeholder จนถึงคอมมิตล่าสุด **แม้ข้อความคอมมิตล่าสุด ("seed: ผูกข้อมูลตัวอย่างกับ uid จริงจาก Firebase Authentication") จะบอกว่ามีการ seed ข้อมูลลง Firebase จริงแล้วก็ตาม** — จึงมีความเป็นไปได้ว่าการ seed นั้นทำกับโปรเจกต์ Firebase อื่น (เช่นบน environment ของผู้พัฒนาเอง) ไม่ใช่กับค่าที่อยู่ใน repo นี้ ผลคือ **repo นี้ต่อฐานข้อมูลจริงไม่ได้เลย**
- **สถานะคีย์ AI:** มีไฟล์ `js/ai-config.js` อยู่จริง (ไม่ได้อยู่ใน git เพราะถูก `.gitignore` กันไว้) แต่ค่า `OPENROUTER_API_KEY` ยังเป็น placeholder ข้อความ "ใส่ API key จาก openrouter.ai ตรงนี้" — **ยังไม่มีคีย์จริง**
- **บัญชีทดสอบที่ใช้ได้:** **ไม่มีเลย** เพราะหน้าล็อกอิน/สมัครสมาชิกถูกปิดการใช้งาน (ดูรายละเอียดข้อ US-08) — พยายามพิมพ์ข้อความลงช่องอีเมลของหน้าสมัครสมาชิกด้วย Playwright โดยตรง (`fill` เข้าฟิลด์ที่ถูก mark `disabled`) แล้วได้รับ `TimeoutError: element is not enabled` ยืนยันว่าฟิลด์ถูกปิดจริงในระดับ DOM ไม่ใช่แค่ภาพลวงตา — **จึงไม่สามารถสมัครสมาชิกหรือล็อกอินด้วยบทบาทใดได้เลยในสภาพแวดล้อมนี้**
- **สรุปนัยสำคัญ:** เนื่องจากกฎเหล็กข้อ 1 ห้ามแก้ไฟล์ใน `js/**` (รวม `js/firebase-config.js`) ไม่ว่ากรณีใด และไม่มีบัญชี/โปรเจกต์ Firebase จริงให้ทดสอบ ผลคือ **User Story ส่วนใหญ่ที่ต้องพึ่งการล็อกอินหรือฐานข้อมูลจริงทดสอบไม่ได้ในรอบนี้** รายงานนี้จึงเน้นตรวจสิ่งที่ทดสอบได้จริงโดยไม่ต้องล็อกอิน (route guard, ข้อความแจ้งเตือนภาษาไทย, การไม่ค้าง/ไม่มี error ดิบ, ความรับผิดชอบต่อจอมือถือ) และรายงานส่วนที่เหลือว่า "ทดสอบไม่ได้" ตามกฎเหล็กข้อ 2

## 3. รายละเอียดข้อที่ไม่ผ่าน

### บั๊ก: ปุ่ม "ออกจากระบบ" แสดงผลอยู่ในแถบเมนูแม้ยังไม่ได้ล็อกอิน

- **หน้าไหน:** ทุกหน้าที่มีแถบเมนู (navbar) เท่าที่เข้าถึงได้โดยไม่ล็อกอิน — ทดสอบซ้ำบน `login.html` และ `signup.html` ทั้งขนาดจอ desktop (1280×800) และมือถือ (375×812)
- **ขั้นตอนทำซ้ำ:**
  1. เปิด `http://localhost:3000/login.html` โดยไม่ล็อกอิน (สภาพแวดล้อมนี้ล็อกอินไม่ได้อยู่แล้วเพราะ Firebase ไม่ได้ตั้งค่า แต่บั๊กนี้เกี่ยวกับสถานะ "ยังไม่ได้ล็อกอิน" ไม่เกี่ยวกับ Firebase)
  2. มองที่มุมขวาบนของแถบเมนู
  3. สังเกตว่ามีทั้งปุ่ม "ออกจากระบบ" และลิงก์ "เข้าสู่ระบบ" ปรากฏพร้อมกัน
  4. ตรวจสอบด้วย `document.getElementById('btn-logout')` พบว่า `.hidden === true` (attribute `hidden` ถูกตั้งค่าไว้ถูกต้องโดย JS) แต่ `getComputedStyle(btn).display === "block"` (ไม่ใช่ `none`) — ปุ่มจึงถูกมองเห็นได้ทั้งที่ควรถูกซ่อน
- **สิ่งที่ควรเกิด:** ตาม logic ที่ตั้งใจไว้ (เห็นจาก HTML: `<button id="btn-logout" hidden>`) เมื่อยังไม่ได้ล็อกอิน ปุ่ม "ออกจากระบบ" ควรถูกซ่อน เหลือแต่ลิงก์ "เข้าสู่ระบบ" เพียงอย่างเดียว
- **สิ่งที่เกิดจริง:** ปุ่ม "ออกจากระบบ" ยังคงมองเห็นได้และกดได้ (แม้กดแล้วไม่มีอะไรเกิดขึ้นในสภาพนี้เพราะยังไม่มี session ให้ออก) เกิดจาก `css/style.css` บรรทัด 77-88 มีกฎ `button, .btn { ... display: inline-block; }` ซึ่งชนกับสไตล์ดีฟอลต์ของเบราว์เซอร์ `[hidden] { display: none }` — เพราะ selector `button` มีความสำคัญเท่ากันแต่มาทีหลังใน cascade จึงชนะและทำให้ attribute `hidden` ไม่มีผลกับ `<button>` ใด ๆ ในเว็บนี้เลย (เป็นข้อสังเกตจากการอ่านโค้ด CSS เพื่ออธิบายสาเหตุ ไม่ได้แก้ไขไฟล์)
- **ความรุนแรง:** LOW — ไม่กระทบความปลอดภัยหรือข้อมูล (กดแล้วไม่มีผลข้างเคียงที่เป็นอันตรายในสภาพที่ทดสอบได้) แต่สร้างความสับสนต่อผู้ใช้และขัดกับ UX ที่ตั้งใจไว้ ควรตรวจต่อว่าเมื่อมีระบบล็อกอินจริงแล้ว การกด "ออกจากระบบ" ตอนที่ยังไม่ได้ล็อกอิน (ซึ่งไม่ควรมีปุ่มให้กดได้ตั้งแต่แรก) จะพังหรือไม่

## 4. ข้อที่ทดสอบไม่ได้ พร้อมเหตุผล

รายการทั้งหมดด้านล่างติดปัญหาเดียวกันคือ **`js/firebase-config.js` ยังเป็น placeholder** ทำให้ Firebase Authentication และ Cloud Firestore เชื่อมต่อไม่ได้จริง ส่งผลให้หน้า `login.html` และ `signup.html` ปิดการใช้งานฟอร์มทั้งหมด (ยืนยันแล้วว่าฟิลด์ถูก `disabled` จริงในระดับ DOM) และหน้าที่ต้องล็อกอินก่อนทุกหน้า (`leave-requests.html`, `new-leave-request.html`, `leave-request-detail.html`, `leave-types.html`, `dashboard.html`) ถูก route guard เด้งกลับไปหน้า `/login` ทันที **ตามกฎเหล็กข้อ 1 ห้ามแก้ไฟล์ `js/**` ทุกกรณี จึงไม่สามารถใส่ค่า Firebase จริงเพื่อปลดล็อกการทดสอบต่อได้**

- **US-01 (หน้ารายการใบลา):** ทดสอบคอลัมน์ตาราง/ชื่อภาษาไทย/ป้ายสถานะ/คลิกเข้ารายละเอียด/ข้อความ "ยังไม่มีใบขอลาในระบบ"/ค้นหา-กรอง-เรียงลำดับ ไม่ได้เลย เพราะเข้าหน้านี้ไม่ได้
- **US-02 (ยื่นใบลาใหม่):** ทดสอบฟอร์ม/dropdown ประเภทจาก DB จริง/การบันทึก/สถานะเริ่มต้น "รอพิจารณา"/ปุ่มยกเลิก ไม่ได้เลย
- **US-03 (รายละเอียดใบลา):** ทดสอบการแสดงผลครบช่อง/ลำดับความเห็นเก่า→ใหม่/ข้อความ "ยังไม่ได้กำหนดผู้อนุมัติ" ไม่ได้เลย
- **US-04 (เปลี่ยนสถานะ):** ทดสอบปุ่มอนุมัติ/ไม่อนุมัติ, การล็อกสถานะหลังตัดสินใจแล้ว, การห้าม employee เปลี่ยนสถานะ ไม่ได้เลย เพราะต้องมีบัญชี manager/hr ที่ล็อกอินได้จริง
- **US-05 (เขียนความเห็น):** ทดสอบการส่งความเห็น/การกันข้อความว่าง/ตำแหน่งเก็บข้อมูลใน subcollection `approvals` ไม่ได้เลย
- **US-06 (จัดการประเภทการลา):** ทดสอบเพิ่ม/แก้/ลบประเภท, การเห็นผลใน dropdown ของหน้ายื่นใบลาทันที, การจำกัดสิทธิ์เฉพาะ hr ไม่ได้เลย
- **US-07 (ลบใบลา):** ทดสอบปุ่มลบ, หน้าต่างยืนยันก่อนลบ, ผลลัพธ์หลังลบจริง, การล็อกปุ่มลบเมื่อไม่ใช่สถานะ "รอพิจารณา" ไม่ได้เลย
- **US-08 (ล็อกอิน/แยกสิทธิ์) — ส่วนที่ทดสอบไม่ได้:**
  - สมัครสมาชิกสำเร็จแล้วเกิดเอกสารใน `users` พร้อม `role: employee` — ทดสอบไม่ได้ (สมัครไม่ได้เลย)
  - `requesterId` ของใบลาใหม่ตรงกับ uid ที่ล็อกอินจริง — ทดสอบไม่ได้
  - ผู้ขอลาคนหนึ่งเปิดใบลาของอีกคนไม่ได้ (ต้องมี 2 บัญชี employee ทดสอบจริง) — ทดสอบไม่ได้
  - manager/hr เปิดได้ทุกใบ — ทดสอบไม่ได้
  - กฎเฝ้าข้อมูลครอบ subcollection `approvals` ด้วย — ทดสอบไม่ได้ (อ่านแค่ `firestore.rules` เป็นโค้ดแล้วเดาว่าใช้ได้ ไม่ถือเป็นการทดสอบจริงตามกฎเหล็กข้อ 2 จึงไม่รายงานว่าผ่าน)
- **US-09 (ปุ่ม AI):** ทดสอบไม่ได้ทั้งเพราะเข้าหน้ายื่นใบลาไม่ได้ (ต้องล็อกอิน) และเพราะยังไม่มีคีย์ OpenRouter จริงใน `js/ai-config.js`
- **US-10 (ค้นหา/กรอง/เรียงลำดับ):** รวมอยู่ใน US-01 — ทดสอบไม่ได้ด้วยเหตุผลเดียวกัน

**ส่วนที่ทดสอบได้จริงของ US-08 (สรุปแยกจากตารางด้านบน):**
- หน้า `login.html` และ `signup.html` แสดงข้อความเตือนภาษาไทยชัดเจน ("⚠️ ยังไม่ได้ตั้งค่า Firebase — หน้า...จึงยังใช้งานไม่ได้" พร้อมวิธีแก้) และปิดฟอร์มทั้งหมดแทนที่จะปล่อยให้กดแล้วพัง/ค้าง/ขึ้น error ดิบ — ตรงตามกฎเหล็กข้อ 3 (ไม่ใช่บั๊ก เป็นการจัดการสถานะ "ยังไม่ได้ตั้งค่า" ที่ทำได้ดี) — **ผ่าน**
- คนที่ไม่ได้ล็อกอินเข้าหน้าที่ต้องมีสิทธิ์ (`leave-requests.html`, `new-leave-request.html`, `leave-request-detail.html?id=lr001`, `leave-types.html`, `dashboard.html`) ไม่ได้จริง ถูกเด้งไป `/login` ทันทีทุกหน้า ไม่มีการวนซ้ำ — **ผ่านในระดับ route guard ฝั่ง client** (ข้อควรระวัง: นี่เป็นเพียงการป้องกันระดับ UI เท่านั้น ยังไม่ได้พิสูจน์ว่า Firestore Security Rules จริงบล็อกการอ่านข้อมูลตรง ๆ ผ่าน SDK ด้วย เพราะไม่มีฐานข้อมูลจริงให้ยิง request ทดสอบ)

## 5. ข้อเสนอแนะ (ความเห็นเท่านั้น ไม่ใช่ผลทดสอบ)

1. **ให้ทีมพัฒนาใส่ค่า Firebase จริงลง `js/firebase-config.js`** (หรือมอบไฟล์ config/บัญชีทดสอบแยกให้ QA) ก่อนรอบทดสอบถัดไป มิเช่นนั้น US-01 ถึง US-10 เกือบทั้งหมดจะทดสอบซ้ำแล้วยังติดปัญหาเดิม
2. **เตรียมบัญชีทดสอบ 3 บทบาท** (employee, manager, hr) พร้อมรหัสผ่านที่ปลอดภัยสำหรับ QA โดยเฉพาะ (ใช้อีเมล `@example.com` เท่านั้น) และควรมีบัญชี employee อย่างน้อย 2 บัญชี เพื่อทดสอบกรณี "ผู้ขอลาคนหนึ่งเปิดใบลาของอีกคนไม่ได้" ตาม US-08
3. **แก้ไข CSS ที่ทำให้ `hidden` attribute ใช้ไม่ได้กับ `<button>`** เช่นเพิ่มกฎ `[hidden] { display: none !important; }` ไว้ท้ายไฟล์ `css/style.css` เพื่อให้ปุ่ม "ออกจากระบบ" ไม่โผล่มาตอนยังไม่ได้ล็อกอิน (เป็นเพียงข้อเสนอ ให้ทีมพัฒนาตัดสินใจแก้เอง เนื่องจากกฎการทดสอบห้าม QA แก้โค้ด)
4. เมื่อเชื่อมฐานข้อมูลได้แล้ว ควรทดสอบเพิ่มเติมเรื่องการยิง request อ่าน Firestore ตรง ๆ ผ่าน browser console (ไม่ผ่าน UI) ด้วย เพื่อพิสูจน์ว่า Firestore Security Rules บล็อกจริง ไม่ใช่แค่ route guard ฝั่ง client เท่านั้น
